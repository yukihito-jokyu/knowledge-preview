# フロントエンド実装

このリポジトリのReact SPAを、依頼された範囲で実装する。コメントと説明は日本語で記載する。

## Ponytailとの併用

実装時は [ponytail](../ponytail/SKILL.md) を併用し、既存実装・標準機能を優先する。明示されたモードを尊重する。ユーザーがPonytailを停止している場合は適用しない。簡略化のために、対象Issueの要件、本スキルの責務境界、認可・安全性、必須検証を省略しない。

## 最初に確認するもの

リポジトリルートを確認し、以下を読む。リンクはこのスキルの配置からの相対パスである。バージョンや規則はスキルに固定せず、実行時のファイルを正とする。

- [ARCHITECTURE.md](../../../dev/frontend/ARCHITECTURE.md)：配置、依存方向、生成物、共通化の基準。
- [package.json](../../../dev/frontend/package.json)、[oxlint.config.ts](../../../dev/frontend/oxlint.config.ts)、[Oxfmt設定](../../../dev/frontend/.oxfmtrc.json)：利用できるライブラリ、型・リント・整形の実際の制約。
- 対象画面・機能と近い既存実装、関連テスト、API契約。UI変更では既存の`components/ui`とスタイルも確認する。

`git status --short`と差分を確認する。未追跡ファイルも調べ、開始前からあるユーザーの変更を上書き・巻き戻ししない。

## 配置と実装の判断

1. 期待する動作、入力、成功・失敗条件を整理する。不明なAPIエンドポイントや権限仕様を推測で実装しない。確定済みのUI・型・境界は進め、不明点に依存する箇所を明示する。
2. `routes`はURL・検索状態・認可境界・loaderと画面の接続、機能の`ui`は表示、`model`はquery・mutation・検証、`api`はHTTP契約に配置する。小さな通信でもUIから直接APIを呼ばない。
3. 他機能の型・処理を直接参照しない。同じ機能内の`api`から`model`の型参照は許される。共通化はARCHITECTUREの基準で判断し、import制限を避けるだけの移動や再エクスポートをしない。
4. TanStack Queryのquery keyにID・検索条件を反映し、mutation後にどのキャッシュを更新するかを決める。URL共有する状態と一時的なフォーム状態を混同しない。
5. 未処理Promise、型のない外部データ、状態分岐の欠落を確認する。`any`、根拠のない型アサーション、抑制コメント、`void`の追加だけで検査を通さない。抑制が必要なら理由と適用範囲を限定する。
6. 既存のUI部品とテーマを使う。変更に関係する読み込み中・空・エラー・送信中の表示、二重送信、ラベル、キーボード操作を実装する。画面変更では利用できる実行環境で見た目と操作を確認し、確認できない部分を報告する。

サーバーの認可を画面の非表示で代替しない。Markdownの生HTML、秘密情報、平文トークン、API契約に関わる変更では、既存の責務境界を確認する。

`routeTree.gen.ts`は手編集しない。ルート追加・移動時は、型検査より先に`pnpm --dir dev/frontend run build`または既存の開発サーバーでルート定義を生成する。未生成のルートによる型エラーを型アサーションで回避しない。

## 整形と検証

動作変更に見合うテストを対象ファイルの隣へ追加・更新する。成功条件だけでなく、その変更で壊れやすい失敗条件を選ぶ。空行・文言だけの変更に実装をなぞるテストを追加しない。

実装変更時はリポジトリルートから以下を実行する。最新のpackage.jsonでコマンドを確認して使う。

```bash
pnpm --dir dev/frontend run fmt
pnpm --dir dev/frontend run lint:fix
pnpm --dir dev/frontend run lint
pnpm --dir dev/frontend run fmt:check
pnpm --dir dev/frontend run typecheck
pnpm --dir dev/frontend run test
pnpm --dir dev/frontend run build
```

無関係な未整形ファイルがある場合、整形・自動修正は変更対象のパスに限定し、全体検査の既存の失敗と今回の失敗を区別する。自動修正後の差分を確認する。Oxfmtによる改行と空行ルールの両方が通ることを確かめる。

ルート生成のために先行して実行したbuildなど、同じ最終コードで成功済みの検証は重ねて実行しなくてよい。

リント成功は仕様の正しさを保証しない。特に間接参照・計算した動的import、非同期の失敗伝播、API応答の実行時検証はコードでも確認する。リントを通すためにルールを弱めたり、依存を迂回したりしない。

## 完了時の報告

何ができるようになったか、主な変更、実行した検証と結果、未確認事項を簡潔に記載する。根拠を示す場合は実際のコードを短く引用し、現在の絶対パスと行番号へのリンクを付ける。コミット・PR作成・公開は、その依頼または既存の承認がある場合に行う。
