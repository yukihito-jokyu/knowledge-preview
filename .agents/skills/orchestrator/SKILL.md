# Issue実装のオーケストレーション

メインはIssue受付、委譲、報告統合、計画と進捗の管理、人間との確認を行う。製品・テストの調査、実装、修正、レビュー、検証コマンドの実行はサブエージェントへ任せる。メインが子の報告や差分一覧を確認して完了判定することは、実装代行とは区別する。

## 受付と成果物

IssueのURL、番号または番号を伴う本文を受け取る。別リポジトリの同番号を混同しないよう対象リポジトリも確認する。指定が足りない場合は必要な情報だけ質問する。URLや番号から本文を取得する作業も、新規の調査担当へ委譲する。取得不能なら貼付本文を依頼し、推測で要件を作らない。

成果物は実行対象リポジトリの `docs/work/<Issue番号>/plan.md` と `logs/` に置く。`docs/work/` はGit管理対象外のままにする。

```text
docs/work/<Issue番号>/
├── plan.md
└── logs/
    ├── 001-research-backend.md
    ├── 002-research-frontend.md
    └── …
```

メインは [計画テンプレート](assets/plan-template.md) を使ってplanを編集する。「状態と承認」という見出しは作らず、作業状況は対応表で管理する。Issue出典と承認対象を識別できる計画版は冒頭の短い文章に記載する。受け入れ基準、作業ID、シナリオIDは各々1からの数字連番、E2E表の要件列は受け入れ基準の番号とする。

既存plan/logsがある場合は消したり新規実行扱いにしたりしない。Issue・計画版・承認記録・作業状況・差し戻し履歴を読み、未確定箇所から再開する。承認を確認できない計画は実装へ進めず人間へ確認する。後続の作業IDとログ番号は既存最大値の次から割り当て、過去の番号を変更しない。

## サブエージェントの起動規則

調査、初回実装、修正、レビュー、再レビュー、audit、debt、再検証のすべてで新規サブエージェントを作る。終了済みagentへのfollowupや再開で使い回さない。実行中の担当への状況確認・同一作業の連絡は可能だが、別作業を追加しない。担当が停止した場合も新規担当へ引き継ぐ。

サブエージェントにはさらに子を起動させない。メインが起動枠、担当範囲とIDを一元管理する。利用可能枠を超える場合は先行条件を満たした作業を待ち行列に入れる。サブエージェント機能が使えないときは制約を報告し、メインで代行して完了扱いにしない。

起動時に次を渡す。

- Issue出典・本文、計画版・承認状況、作業IDと元の実装作業ID。
- 担当目的、使用スキルの絶対パス、読み取り・変更可能な範囲、完了条件。
- 対象リポジトリの絶対パス、AGENTS.md、変更前の差分情報、先行担当のログ。
- 通常レビュー・最終チェックそれぞれの差し戻し回数と未解決指摘。
- 一意な報告パスと [報告テンプレート](assets/log-template.md)。担当自身が記入し、秘密値を含めない。
- 新しい子を起動しないこと、他担当のログ・担当範囲を編集しないこと。

全担当は作業開始前に既存差分を確認する。既存のユーザー変更を上書き・巻き戻しせず、完了時に自分の変更を識別して報告する。メインはログの存在と内容を確認して対応表を更新する。報告欠落を完了扱いにしない。失敗した担当のログも残し、新規担当には別のログを割り当てる。

## 調査フェーズ

すべての調査担当を「スキルなし」で起動する。backend-review等を調査用に流用しない。調査対象に応じBE、FE、E2E・基盤などに分ける。不要な担当を固定で作らない。読み取り専用でIssue、README、ADR、対象層のARCHITECTURE、実コード・呼出し元・近いテスト、docs/testing.md、E2E README・Taskfileを調べさせる。

各担当に、要件・仕様・現在の実装の区別、根拠の絶対パス・行番号・短い引用、不足基盤、未確定事項、変更ファイル案、契約・依存関係、担当分割、E2Eシナリオ案を報告させる。共通規約のシナリオ名を列挙するだけで済ませない。

メインは報告を統合し、食い違いがあれば追加の新規調査担当へ確認させる。計画には初期状態・ユーザー権限・入力値・操作・期待API応答・保存結果・再読込後の状態・失敗・境界・回帰観点と、受け入れ基準との対応を含める。対象外の観点は理由を残し、全件をE2Eへ重複実装せず単体・契約との分担を明記する。

共有APIの契約、変更担当範囲、先行条件、並行可否、必要な環境・fixtureを確定する。APIや未実装基盤を推測で埋めない。実装を左右する不明点が残る場合は人間へ返す。planを提示し、その版への明示的承認後だけ実装を起動する。このスキルへの一般的な実行依頼を、未提示の計画への承認とみなさない。

## 使用スキルと担当分割

| 作業 | 実装担当 | レビュー担当 |
| --- | --- | --- |
| バックエンド | backend-implement + ponytail | backend-review + ponytail-review |
| フロントエンド | frontend-implement + ponytail | frontend-review + ponytail-review |
| E2E・fixture・テスト環境 | e2e-implement + ponytail | e2e-review + ponytail-review |
| 調査 | スキルなし | 該当なし |
| 対応スキルのない作業 | スキルなし | スキルなし |

使用するスキルは対象リポジトリの `.agents/skills/` にあるものを起動時に指定する。対象外のスキルを無理に割り当てず、新しいスキルの作成をIssue実装に含めない。Ponytail停止の明示指示がある場合はそれを優先し、audit/debtの実施要件と衝突するなら人間へ確認する。Ponytailは既存規約、受け入れ基準、安全性、必須テストの省略理由にしない。

並行実装は契約が確定し、書込みファイル・共有環境が競合しない場合だけ許可する。router、依存定義、lockfile、DB migration等の共有変更は単一担当に割り当てる。競合が判明したら停止範囲を決め直列化する。レビュー対象とaudit/debt対象はチェック完了まで変更を止め、同じ差分を見せる。

## 実装・レビューの反復

各実装担当が対象層の検査と報告を終えたら、新規レビュー担当を起動する。レビュー担当はコードを直さず、合格・差し戻し・判断不能を分け、根拠と対象ファイルを報告する。

通常レビューの差し戻しは元の実装作業ごとに、不合格レビュー1回を1回として数える。指摘件数では数えない。1回目は該当implementスキルの新規担当へ修正を依頼し、別の新規担当で再レビューする。2回目に達したら次の自動修正を始めず人間へ返す。新しい作業ID・担当・フェーズになっても回数をリセットしない。

指摘が仕様の未確定に依存する場合は不具合と断定せず人間へ判断を求める。受け入れ基準・契約・実装範囲・検証期待値が変わる場合はplanを改訂し再承認する。承認済み範囲の通常修正では承認を取り直さない。

## 実装フェーズの最終チェック

全実装レビューの合格後、`ponytail-audit` と `ponytail-debt` を別々の新規サブエージェントで並行実行する。どちらも読み取り専用で、自分のログだけを書ける。全体の問題を調べつつ、今回の変更に対する修正事項と既存の対象外問題を区別させる。

修正が必要なら該当implementスキルを使う新規担当へ直接差し戻す。先に別レビューを挟んで判断をやり直す手順にはしない。複数層なら指摘と担当範囲を対応付け、競合しない単位で起動する。

最終チェックの差し戻しは通常レビューとは別に元の実装作業ごとに管理する。同じ変更版に対するaudit/debtの結果を統合して1回と数える。1回目は新規実装担当で修正→新規の対象層レビュー→新規audit/debt。修正後レビューの不合格は通常レビュー回数へ加算する。最終チェックが2回目の差し戻しになれば自動修正を停止して人間へ返す。auditとdebtを跨いでも、担当が交代しても累計を引き継ぐ。

対象外の既存問題は記録のみとし、修正範囲を勝手に広げない。実行失敗・ログ欠落・判断不能はチェック未完了。必要な新規調査担当や人間への確認で解消し、解消まで検証フェーズに進まない。

## 検証フェーズ

新規E2E担当が `e2e-implement + ponytail` で承認済みシナリオとfixtureを実装し、現行Taskfileに従って実行する。専用のE2E_RUN_IDで起動・初期化・テスト・後片付けを行わせる。共有成果物や環境へ複数担当を同時に書き込ませない。

成功なら新規の `e2e-review + ponytail-review` 担当がシナリオ対応・偽陽性・分離・cleanup・実行証跡をレビューする。テストの問題でも同じレビュー担当が判定し、差し戻しなら新規E2E実装担当→再実行→新規E2Eレビューへ進む。通常レビューの2回目で人間へ返す。

製品不具合は原因となる元の実装作業へ結び付け、対象層の新規implement担当→新規review→新規audit/debt→E2E再実行へ戻す。元の差し戻し回数を維持する。原因不明ならスキルなしの新規調査担当へ分離して依頼する。

環境要因・実行不能は未検証として停止範囲と再開条件を報告する。環境修正が承認範囲内なら新規の該当担当へ依頼し、解消後は新規E2E担当で再実行する。0件、skip、一覧表示、環境疎通、モック正常応答だけをE2E成功としない。実際のコマンド、終了コード、件数、ブラウザ、失敗理由、証跡パスをログに残させる。

## 停止・再開・完了

人間へ返す際は、対応表を「人間判断待ち」にし、未解決指摘、影響、通常レビュー／最終チェックの回数、過去の対応ログ、判断してほしい点を示す。対象と依存作業を止め、独立作業を継続する場合は明示する。人間の返答なしに再開しない。再開を承認された場合は許可された修正範囲・追加試行数を確認して記録し、過去の回数を消して上限を回避しない。

全受け入れ基準、実装・E2Eレビュー、audit/debtの対応、実E2E成功、後片付けをログと照合して完了報告する。未実行項目や残る制約を隠さない。コミット・PR・Issueコメント等は別途依頼されている場合だけ行う。

## 形式検査と限界

`scripts/check_plan.py` は任意の構造化計画入力を検査する補助であり、agentを起動・制御するランタイムではない。使う場合は同梱の `--help` と [入力仕様](references/check-input.md) を読み、計画入力または実行記録の写しを検査する。通常はテンプレートに沿ってメインがplanを更新するだけでよく、JSONの二重管理を必須にしない。

スクリプトの形式検査や模擬イベント検査に成功しても、実際の承認・agent起動・シナリオ網羅・実装品質を保証しない。メインは実ログと現在の計画を照合する。
