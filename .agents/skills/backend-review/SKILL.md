# バックエンドレビュー

## レビュー範囲を決める

ユーザーが指定したファイル・差分・比較先を対象にする。指定がない場合は `git status --short`、ステージ済み・未ステージの差分、関連する未追跡ファイルから範囲を決めて明示する。比較先のブランチ名は推測で固定しない。

パスはリポジトリルートを基準に扱う。レビュー前に [ARCHITECTURE.md](../../../dev/backend/ARCHITECTURE.md)、[Taskfile.yml](../../../dev/backend/Taskfile.yml)、[.golangci.yml](../../../dev/backend/.golangci.yml) を読む。以下のリンクはこのスキルからの相対パスである。
差分だけで判断せず、呼び出し元、依存先、関連テストを追い、到達可能な問題か確かめる。

レビューのみの依頼ではソースを編集せず、`task fmt` や自動修正オプションを実行しない。修正も依頼されている場合は、その範囲で実装へ進める。

## 変更に応じて見る観点

全項目を一律に指摘せず、変更箇所から生じる具体的な影響を調べる。

| 対象 | 確認すること |
| --- | --- |
| 配置・依存 | Use caseとHTTPは機能名のファイルを直下に置いているか。レスポンスは `interface/response`、PostgreSQLは `infrastructure/postgres` にあるか。分類だけの階層や不要なラッパーが増えていないか |
| 層の責務 | domainやUse caseへGin・pgx・環境変数の具体的な処理が漏れていないか。依存の組立てが `cmd/api` にまとまっているか |
| API契約 | ルート、入力、ステータス、JSON形式、エラー変換が呼び出し側と整合するか。内部情報を応答へ漏らさないか |
| エラー・外部I/O | エラーを無視していないか。接続・リソースの解放、期限、キャンセル、終了処理が失敗経路でも成立するか |
| DB変更 | SQL引数、結果の扱い、transaction境界、部分失敗時の整合性が妥当か。変更がある場合のみ確認する |
| 認証・認可 | 対象機能に必要なユーザー・所有者・権限の検証が抜けていないか。要件にない仕組みを一律に要求しない |
| テスト | 変更した振る舞いの失敗・境界条件が検証されるか。実装の写しではなく、契約違反で失敗するテストか |
| 検査・文書 | Lintやテストの緩和で問題を隠していないか。移動後のimport・リンク・ARCHITECTURE.mdが実装と一致するか |

ARCHITECTURE.mdの「現在の実装」「未実装」は状況説明として扱う。既知の未実装事項を、今回導入した不具合と混同しない。差分レビューでは新たな問題や悪化した問題を優先し、ファイル全体の監査を依頼された場合は既存の問題も対象にする。
書式の好みはLintの設定へ委ね、別の流儀を欠陥として報告しない。

## 検証

Goコードのレビューでは、環境と対象に応じてリポジトリルートで実行する。

```sh
task --dir dev/backend check
```

これはファイルを書き換えず、Lint・整形検査と全Goテストを実行する。実行前に対象テストの外部接続や副作用を確認する。
テスト成功だけで正しさを断定せず、疑わしい挙動は既存テスト・呼出し経路・必要なら隔離した再現で確かめる。
未実行、環境要因の失敗、コード起因の失敗を区別して報告する。

## 報告

指摘を重要度順に記載する。各指摘は、問題の発生条件、実際に起こる影響、根拠、修正の方向がつながる短い説明にする。

- 重要度は `[P1]`（重大な不具合）、`[P2]`（修正すべき通常の不具合）、`[P3]`（影響が限定的）を目安にし、影響から判断する。
- 根拠には実際の短いコード引用と `[ファイル名 行番号](絶対パス:行番号:1)` を付ける。差分レビューでは問題を導入した箇所を指す。
- 仕様が不明な懸念は断定せず、確認事項として指摘と分ける。好みや将来の仮定だけで件数を増やさない。
- 問題がなければ「指摘なし」とし、確認範囲・検証結果・残る未検証事項を簡潔に示す。完全性の保証はしない。

レビュー結果はユーザーに返す。依頼されていないコミットやPRコメント投稿は行わない。
