# フロントエンドレビュー

変更によって利用者や保守に具体的な問題が生じるかを調べる。日本語で、再現条件と影響が分かる指摘を返す。レビューだけの依頼ではソースの修正や自動修正を行わない。

## 範囲と根拠

1. ユーザーが指定したファイル・差分・PRを対象とする。指定がなければステージ済み・未ステージ・未追跡のフロントエンド変更を確認する。ブランチ比較は指定されたベースを使い、不明なら根拠を調べるか確認する。勝手にmainやHEADとの差分へ置き換えない。
2. [ARCHITECTURE.md](../../../dev/frontend/ARCHITECTURE.md)、[package.json](../../../dev/frontend/package.json)、[oxlint.config.ts](../../../dev/frontend/oxlint.config.ts)、[Oxfmt設定](../../../dev/frontend/.oxfmtrc.json)を読む。実際の制約と既存パターンを判断基準にする。
3. 差分だけで判断せず、変更された関数の呼び出し元、関連する型・API契約・テストまで追う。生成ルートは変更元のルート定義と生成手順を確認し、生成物の手編集を解決策にしない。

## 変更に応じて確認する観点

| 対象 | 確認すること |
| --- | --- |
| 配置・依存 | routesに業務処理が混ざっていないか。UIがmodelを経由しているか。他機能の型も含む直接参照、共通層からの逆参照、循環、再エクスポートや別名での迂回がないか。 |
| API・型 | API契約とDTOが一致するか。外部データを型アサーションだけで信用していないか。nullable・unknownの扱い、認可エラーと通信エラーの区別が適切か。 |
| 非同期・状態 | 処理を待つ順序、失敗伝播、二重送信、競合、Promiseの複数回完了、破棄後の更新が問題にならないか。switch以外の条件分岐にも状態の漏れがないか。 |
| Query・URL | query keyがID・検索条件・利用者の切り替えを適切に区別するか。mutation後の更新、ログアウト時のキャッシュ、一度限りのトークンの扱い、URL復元に問題がないか。 |
| UI | 成功・空・読み込み中・失敗・送信中で操作が成立するか。既存部品の契約、ラベル、フォーカス、キーボード操作、狭い画面での表示が保たれているか。 |
| 境界の安全性 | クライアント側の非表示だけに認可を依存していないか。Markdownの生HTMLや秘密情報の露出など、変更が具体的に引き起こす問題がないか。 |
| テスト | 変更の重要な振る舞いと失敗条件を検証しているか。モックで問題を隠していないか。テストの存在だけで正しさを判断していないか。 |

すべての観点を指摘として出力する必要はない。対象の変更に関係するものだけ調べ、未実装の将来機能や好みの設計を不具合として扱わない。

## 検証方法

必要な再現やテストを優先する。整形・リントは自動修正せず、次のコマンドを使う。実行するコマンドは最新のpackage.jsonで確認する。

```bash
pnpm --dir dev/frontend run lint
pnpm --dir dev/frontend run fmt:check
pnpm --dir dev/frontend run typecheck
pnpm --dir dev/frontend run test
```

ビルド・ルーティング・バンドルに関わる場合は`pnpm --dir dev/frontend run build`も確認する。生成物や既存の作業状態への影響がある場合は隔離した作業先で検証する。レビューのためにユーザーの差分を整形・巻き戻ししない。

実行済み・未実行・失敗を区別する。既存の失敗は今回の変更による回帰と区別する。UIを動かしていない場合は目視・操作確認済みと書かない。

リントは補助証拠として使う。import文字列への制限は全経路を解決する検査ではなく、Promiseのルールも全パターンを検出する保証はない。疑わしい箇所は具体的な実行経路か最小再現で確認する。

## 指摘のまとめ方

指摘があれば重大なものから記載する。各指摘は一つの問題に絞り、次をつながった文章で説明する。

- 発生条件：どの入力・操作・状態で問題になるか。
- 根拠：現在の絶対パスと行番号へのリンク、および該当コードの短い引用。
- 影響：利用者または開発者に何が起きるか。
- 修正の方向：責務や動作をどう直すか。依頼されていない修正は適用しない。

重大度はP0（緊急）、P1（優先修正）、P2（通常修正）、P3（軽微）を目安とし、実際の影響で決める。仮定が未確認のものは確定した指摘と分ける。差分レビューでは原則として変更に起因する問題を指摘し、範囲外の既存問題を混ぜない。

最後に確認範囲、検証結果、残る不確実性を短く添える。指摘がなければ「確認した範囲では指摘なし」と記載し、件数を埋めるための指摘を作らない。GitHubへのレビュー投稿は明示的な依頼がある場合に行う。
