# E2Eレビュー

作成されたE2Eが対象の仕様違反を検出できるか、再現可能に実行できるかを確認する。レビューのみの依頼ではソースの変更・整形・自動修正をしない。

## Ponytailとの併用

レビュー時は [ponytail-review](../ponytail-review/SKILL.md) を併用し、過剰設計も確認する。ユーザーがPonytailを停止している場合は適用しない。本スキルの正しさ・安全性・回帰の確認を主とし、簡略化の指摘は区別する。リポジトリ規約が要求する構造・検証を過剰設計として削除提案しない。オーケストレーション中はメインへ報告し、修正が必要ならメインが別の新規実装担当へ引き継ぐ。単独レビューの依頼だけで修正担当を起動しない。

## 対象と判断基準

- 指定された差分・ファイル・PRを対象とする。指定がなければ現在のE2Eと関連環境のステージ済み・未ステージ・未追跡の変更を確認する。比較元を勝手にmainへ置き換えない。
- 対象Issueの具体的なシナリオと[横断検証規約](../../../docs/testing.md)を読む。規約が要求する期待結果と、specが実際に観測する結果を対応付ける。
- [E2E README](../../../dev/frontend/e2e/README.md)、[Playwright設定](../../../dev/frontend/playwright.config.ts)、[E2E型設定](../../../dev/frontend/tsconfig.e2e.json)、[共通fixture](../../../dev/frontend/e2e/fixtures/test.ts)を確認する。環境差分なら[Taskfile](../../../Taskfile.yml)、[Compose](../../../dev/compose.test.yaml)、該当Dockerfile・スクリプトも追う。
- 実API・画面との契約が疑わしい場合は対象の製品実装を確認する。テストが通ることだけで、仕様に合っていると判断しない。

## 差分に応じた確認観点

| 観点 | 確認すること |
| --- | --- |
| 誤った成功 | 操作が実際に実行されるか。assertionが待たれているか。エラーを握りつぶしていないか。トーストや固定モックだけで保存・認証成立と判定していないか |
| 名前と観測内容 | 名前が条件・期待結果の一文になり、assertionの内容と一致するか。独立した振る舞いを一つのtestへまとめていないか |
| シナリオと境界 | 対象Issueの成功・失敗条件、権限、再取得結果を観測しているか。環境疎通や未実装501を業務シナリオの完成と誤認していないか |
| 実接続 | SPA→実API→保存結果まで必要な境界を通っているか。製品の変換関数から期待値を作り、同じ不具合を再現していないか |
| 安定性 | 固定sleep、共有状態、実行順、時刻、曖昧なlocatorに依存していないか。応答待機の登録が操作に間に合うか |
| 分離と解放 | 実行ID・テストID、ユーザー、オブジェクト、ブラウザprofileが分離されるか。失敗時も解放され、他の実行を削除しないか |
| 認証・秘匿 | 共通ブラウザfixtureを使い、TLSと実OAuthの境界を保持するか。Cookie・トークン等がログ、レポート、永続領域に残らないか |
| 実行対象 | testMatchやCOPYが新規・移動後のファイルを含むか。.example・0件・skipで検証漏れにならないか。ローカルの旧イメージだけで確認していないか |
| コマンド制御 | 起動→初期化→必要なseed→テストの順序、終了コード、成果物回収、Composeプロファイルを含むdownが成立するか |
| 配置 | 規約の責務に沿っているか。spec同士のimportや巨大な共通処理が検証内容を隠していないか |

対象に関係する観点だけを調べる。将来機能の未実装が明示されている場合、存在しないこと自体を今回の回帰として指摘しない。ただし、完成を宣言している範囲でその未実装を成功扱いにしている場合は問題として扱う。単なる好みの分割を不具合にしない。

## 検証と再現

必要な静的検査は自動修正なしで行う。

```bash
pnpm --dir dev/frontend lint
pnpm --dir dev/frontend fmt:check
pnpm --dir dev/frontend typecheck:e2e
pnpm --dir dev/frontend test:e2e:list
```

依存が不足していれば[E2E README](../../../dev/frontend/e2e/README.md)の準備方法を使う。実行が必要な指摘は、実行専用の環境で該当シナリオを再現する。ソースを書き換える検証が必要なら隔離した作業先を使い、元の差分を変更しない。

実行時は変更を含むイメージをビルドし、一意なE2E_RUN_IDを使う。個別実行の後片付けまで行う。レビューを理由に本番・共有開発環境や他の実行を操作しない。成功・失敗・未実行を区別し、ブラウザを動かしていなければE2E確認済みとは書かない。

## 指摘の出し方

重大なものから、一件につき発生条件→根拠→検出できなくなる不具合や実行への影響→修正の方向をつなげて記載する。根拠にはファイルの絶対パス・行番号へのリンクと実際のコードの短い引用を付ける。重大度はP0〜P3を実際の影響から判断する。

再現していない仮説は確定指摘と分け、範囲外の既存問題を混ぜない。指摘がなければ「確認した範囲では指摘なし」とし、確認範囲・実施した検証・残る不確実性を添える。GitHubへのレビュー投稿は明示的に依頼された場合に行う。
