# フロントエンド・バックエンド横断の検証規約

関連: [Issue #7](https://github.com/yukihito-jokyu/knowledge-preview/issues/7)

## 適用範囲と現在の状態

この文書は、実際のフロントエンド、Go API、PostgreSQL、ファイル保存を接続して確認するAPI契約、認証Cookie、ブラウザE2E、回帰の規約を定める。技術とセキュリティ要件は [ADR-0001](adr/0001-implementation-stack.md) に従う。単一層のテスト配置・検証は [フロントエンド](../dev/frontend/ARCHITECTURE.md#テストの配置と実行) と [バックエンド](../dev/backend/ARCHITECTURE.md#検証範囲) の規約を参照する。

Issue #5・#6は完了扱いだが、この文書の追加時点では、リポジトリに独立した各層の検証規約文書はない。既存のARCHITECTURE.mdを参照元とし、独立文書を追加した際はこのリンクも更新する。

現在のAPIはヘルスチェックまで、画面は主に配置と共通基盤までの実装である。`dev/frontend/e2e/`、`dev/compose.test.yaml`、ルートTaskfileは雛形を配置済みである。既存SPA・API・PostgreSQLの起動、TLS設定、3ブラウザの環境疎通テストを実装している。OAuthの業務処理、業務migration・seed、X01〜X07、横断CIは未実装である。本Issueでは規約を定め、以下の環境とシナリオの実装は対応する機能・基盤変更で行う。規約の完成をE2Eの成功として扱わない。

## 該当条件と責務

| 検証 | 必須になる変更 | 実装担当の責務 | 横断で確認すること |
| --- | --- | --- | --- |
| API契約 | URL、メソッド、DTO、エラー、認証条件、ファイル送受信 | バックエンド担当はHTTP応答と永続化、フロントエンド担当は送信値・応答変換・表示を検証する | 実APIのステータス、JSON、ヘッダーをクライアントが正しく扱い、画面結果と保存結果が一致する |
| 認証Cookie | OAuth、セッション更新、失効、通信設定、ホスト・proxy変更 | バックエンド担当は発行・検証・失効、フロントエンド担当は再取得・遷移・キャッシュ破棄を検証する | 実ブラウザがCookieを保存・送信し、期限切れや失効を画面が正しく扱う |
| ブラウザE2E | 画面の主要操作、画面間遷移、公開表示、HTML隔離 | 機能の実装担当がシナリオとfixtureを追加する。両層の変更箇所をレビューする | 利用者の操作から実API、DB・ファイル、再読込後の表示までを確認する |
| 回帰 | 不具合修正、共有UI・HTTP・認証・DTO・依存・配信設定の変更 | 修正担当が修正前に失敗する観測点を追加し、影響するシナリオIDをPRへ記載する | 修正対象と影響する既存フローが両立する |

PR作成者は該当判定、両層の検証結果、未実施項目の取りまとめを担当する。CI・テスト環境を変更する担当者は再現コマンドと本書を同じPRで更新する。単一層で網羅する入力境界や業務分岐をE2Eですべて重複させず、層を接続しないと見落とす結果をE2Eに残す。

### API契約の確認方法

各機能の実装時に、メソッド・パス、認証条件、request/response DTO、成功・失敗ステータス、エラー構造、公開応答に含めないフィールドを確定する。未確定のAPI名をテスト側で推測しない。仕様とテストの参照を画面IssueまたはPRに残し、DTO変更時は両層を同時に確認する。

契約テストは実Go APIへ送信し、正常系に加え、その変更に該当する未認証、権限違反、入力違反、未存在、競合、内部失敗を検証する。エラーJSONのネストまで確認し、フロントエンドのエラー表示も代表例で接続する。TypeScriptの型宣言やfakeの応答だけでは契約成立としない。

### Cookieとブラウザの確認方法

認証シナリオでは手動Cookie注入でログインを省略せず、OAuth callbackから確認する。後続の知識シナリオでは同じログインfixtureを再利用してよいが、テスト間でブラウザコンテキストを共有しない。

- 応答の`Set-Cookie`とブラウザ内のCookieを確認し、認証Cookieの`HttpOnly; Secure; SameSite=Lax`、`Domain`属性なし、定義したPath・有効期限を検証する。`__Host-`接頭辞を採用した場合はその制約も確認する。
- 認証APIへの送信、JavaScriptから認証Cookieを読めないこと、プレビュー用ホストへの不送信を実ブラウザで確認する。Cookieはポートだけでは分離できないため、プレビューには別ホストを使う。
- access tokenの期限切れ後に更新・再試行でき、更新失敗時には保護画面と認証済みキャッシュが残らないことを確認する。Refresh Tokenのローテーションと旧値再利用によるファミリー失効はサーバー結合テストで網羅し、ブラウザではその失効後に再ログインが必要になることを確認する。
- Cookie認証の更新系APIについて、許可しないOriginからの操作が採用したCSRF対策で拒否されることを確認する。別originのAPIを採用する場合は、資格情報付きCORSの許可・拒否も対象にする。

## 必須の横断シナリオ

以下は共通の最低限の観点であり、そのままで各機能のテスト設計が完了するものではない。**各実装Issueで、該当するシナリオをさらに具体化することを必須とする。** 実装前に、初期状態・ユーザー権限・入力値とファイル・操作順・API応答・保存結果・再読込後の表示・失敗条件と境界値を決め、Issueに記載する。未確定事項は明示し、仕様確定時に更新する。

各行のIDは規約内の参照用とし、テスト名には含めない。対応が必要な場合は、シナリオの日本語名とID・Issueをspecのコメントに記載する。初期データとして所有者A、別ユーザーB、未認証ブラウザを分け、成功表示だけでなく再取得後の結果を判定する。

| ID・操作 | 準備と操作 | 成功条件・回帰条件 |
| --- | --- | --- |
| X01 ログイン | 未認証で保護画面へ移動し、OAuth代替の認可画面からcallbackへ戻る。拒否、不正state、使用済みcodeも試す | 正常時だけ認証状態になり保護画面を表示する。不正時はセッションを作らずエラーを表示する。Cookie属性、期限切れ更新、失効後の遷移は上記の条件を満たす |
| X02 知識登録 | Aが入力と対応ファイルを選び保存する。各採用形式の代表例、入力違反、ファイル上限超過、保存失敗を試す | 実APIで保存され、一覧・再読込で同じ内容になる。10 MiBの境界はサーバーで網羅し、E2Eでは許容例と超過例を確認する。失敗時に成功表示や不完全な知識が残らず、修正して再試行できる |
| X03 知識更新 | Aの既存知識を編集・保存し再取得する。保存失敗とBによる同じIDへの更新も試す | 一覧・編集画面のキャッシュが更新され、永続化した内容と一致する。失敗時は既存の保存内容が保たれ、Bは変更できない。公開内容・下書きの更新は確定した公開仕様どおりになる |
| X04 公開閲覧 | Aが公開した知識を未認証の新規ブラウザで直接開く。非公開、未存在、公開解除後も開く | 公開専用DTOと画面に所有者・メール・トークン・監査・非公開下書き・内部ストレージキーがない。非公開内容は取得できず、公開解除後は再取得や新規ブラウザで読めない。配信キャッシュがある場合は無効化も検証する |
| X05 MCPトークン発行 | Aが画面から発行し、一度だけ表示された値でMCP認証を行う。その後画面移動・再読込・一覧再取得する | 発行直後の値で認証でき、後の画面・一覧APIから平文を復元できない。localStorage、sessionStorage、IndexedDB、Queryキャッシュに平文が残らない。DB・ログ・監査の非保持はサーバー検証と合わせて確認する |
| X06 MCPトークン失効 | Aが発行済みトークンを失効し、同じ値で新しいMCP要求を送る。Bによる失効も試す | 失効結果が再読込後も表示され、旧値の新規要求が拒否される。BはAのトークンを失効できず、Aの他の有効トークンは利用できる |
| X07 プレビュー隔離 | スクリプト、イベント属性、外部通信、フォーム、親画面操作を試みるHTMLを登録し、認証画面と公開画面で閲覧する。Markdownの生HTMLも試す | HTMLが安全化され、別originのiframeの`src`で表示される。空の`sandbox`と`referrerpolicy="no-referrer"`があり、`allow`・`srcdoc`がない。ADRのCSPと`nosniff`が実配信応答にあり、攻撃操作・外部通信が成立せず認証Cookieも送られない。Markdownの生HTMLが実行されない |

X05・X06ではMCPクライアントのUIを追加する必要はない。ブラウザで得た値を、テストプロセス内から実MCPエンドポイントへ送信して利用可否を確認する。秘密値をレポートの引数・失敗メッセージに含めない。

## テスト環境とデータ

現在の実装は既存SPA・Go API・PostgreSQL・TLS・OAuthの雛形までである。MinIOと業務migration・seedは各機能Issueで追加する。環境疎通テストの疎通成功を、以下の完成形の検証成功と混同しない。

完成形の横断環境は`dev/compose.test.yaml`にまとめ、ビルド済みSPA、Go API、PostgreSQL、MinIO、migration、OAuth代替、TLS reverse proxy、Playwright実行用`test`サービスを接続する。Node・Go・DB・MinIO・ブラウザ等はADRの固定方針に従い、ローカルとCIで同じ設定を使う。

アプリは`https://app.knowledge.test`、プレビューは`https://preview.knowledge.test`、OAuth代替は`https://oauth.knowledge.test`をテスト用ホストとする。アプリ配下の`/api`をGo APIへ転送する。コンテナDNSとローカルの名前解決を用意し、テスト専用CAをブラウザ・Go・proxyへ設定する。Secure Cookieの検証をHTTPやTLS検証の無効化で代用しない。ポートや証明書配置は基盤実装時に`dev/frontend/e2e/README.md`へ記載する。

### 初期化と後片付け

1. 実行ごとに一意なCompose project名を使い、専用DBとMinIOボリュームを新規作成する。本番・共有開発DBの接続情報を受け付けない。
2. 空のDBへ本番と同じmigrationを適用し、MinIO bucketを作る。DB疎通だけでなくmigration・seedの終了とAPIの`/ready`成功を待ってからテストを開始する。
3. A・B、公開済み知識、非公開知識、下書き、各形式のファイルを固定fixtureから投入する。時刻・ID・名前を再現可能にし、期限切れはテスト用時計または期限済みデータで作る。長時間sleepを使わない。
4. テストごとにデータの所有者・ID・オブジェクトprefixを分離する。初期導入はworkerを1にし、並列化時はDB・オブジェクトの競合がないことを確認する。他テストの結果を前提にしない。
5. 成否にかかわらず当該projectのコンテナとボリュームを削除する。失敗時も秘密値を除いた診断情報を回収してから削除する。全projectを対象にするpruneは使わない。

seed・初期化はテスト専用コンテナまたはCLIから実行する。製品APIに認証を迂回するseed・ログイン用エンドポイントを追加しない。

### GitHub OAuthの代替

CIと自動E2Eは実GitHubへアクセスしない。GoのOAuth外部依存をテスト用プロバイダへ差し替え、認可・code交換・ユーザー取得をローカルで完結させる。ブラウザからcallback、state検証、PKCE、Cookie発行、ユーザー保存までは実製品の処理を通す。

代替は固定ユーザー、同意拒否、codeの期限切れ・再利用、token交換失敗、ユーザー取得失敗を再現し、PKCEの不一致を拒否する。stateは製品側の検証を省略しない。テスト用設定でのみ接続先を差し替え、本番設定では代替を拒否する。実GitHub固有の接続確認が必要なら非本番OAuth Appによる手動確認を別記し、自動E2E成功の代わりにはしない。

## E2Eのディレクトリ設計

配置・依存・増やし方は本書を正とする。実行方法と現在の未実装箇所は [E2E README](../dev/frontend/e2e/README.md)、個々の処理の注意点はコード内のコメントに置く。サブディレクトリごとにREADMEを増やして同じ規約を複製しない。

以下は追加時の配置先を含む設計である。実ファイルが必要になったディレクトリだけを作成する。

```text
dev/frontend/e2e/
  tests/
    environment.spec.ts       # 環境疎通
    auth/                     # ログイン・セッション
    knowledge/                # 登録・更新
    public-knowledge/         # 公開閲覧
    mcp-tokens/               # 発行・失効
  contracts/
    auth/                     # 認証API契約
    knowledge/                # 知識API契約
    public-knowledge/         # 公開API契約
    mcp-tokens/               # MCPトークンAPI契約
  fixtures/
    test.ts                   # ブラウザ共通の準備・解放
    auth/                     # ユーザー型・生成・認証補助
    knowledge/                # 知識型・入力生成・データ準備
    mcp-tokens/               # トークンの準備・解放
    files/
      markdown/               # 固定Markdownサンプル
      html/                   # 固定HTMLサンプル
  environment/
    frontend/                 # SPAのDockerfile・配信設定
    backend/                  # APIのDockerfile
    proxy/                    # HTTPS・配信先の振り分け
    certificates/             # CA・証明書生成処理
    oauth/                    # OAuth代替サービス
    init/                     # readiness・migration・seed
    runner/                   # PlaywrightのDockerfile・起動処理
  scripts/
    check.sh                  # ホスト側の一括実行と後片付け
  artifacts/
    report/                   # 最新のPlaywrightレポート
    results/                  # 最新のテスト結果
  README.md                   # 実行手順の入口
```

横断テストはフロントエンド配下に置くが、実フロントエンドと実Go APIの接続を検証する。単体・コンポーネントテストは各層の実装の隣に置き、Vitestは`e2e/`を対象から除外する。サービスの接続は`dev/compose.test.yaml`、横断コマンドの入口はルート`Taskfile.yml`で管理する。

Playwright設定は`dev/frontend/playwright.config.ts`、E2Eの型検査設定は`dev/frontend/tsconfig.e2e.json`に置く。テスト探索・型検査の対象は`e2e/`配下とし、設定を移動したときは相対パスも更新する。

E2Eの依存とコマンドは`dev/frontend/package.json`・`dev/frontend/pnpm-lock.yaml`で管理し、E2E配下に別package.jsonやlockfileを作らない。

### 各ディレクトリの責務

| 配置 | 置くもの | 置かないもの |
| --- | --- | --- |
| `tests/` | 操作と期待結果を読むだけで流れが分かる`*.spec.ts`。ブラウザテストは`fixtures/test.ts`からtest・expectを利用する | DB直接操作、コンテナ起動、共通認証処理の複製 |
| `contracts/` | 実APIへ送信し、ステータス・JSON・ヘッダー・秘匿項目を検証する`*.spec.ts` | UI操作の重複、fake応答だけを確認するテスト |
| `fixtures/` | テスト用の入力型、入力生成、準備結果のID対応表、認証・ブラウザライフサイクル。現在の`test.ts`はFirefoxの専用CA・profileを準備して終了時に削除する | 製品の業務判断、テスト本体を隠す巨大なシナリオ実行関数、実DBスキーマを推測したDTO |
| `fixtures/files/` | 意図が分かる名前のMarkdown・HTML等の固定サンプル | 実ユーザーの情報、秘密値、実行で生成したファイル、大容量の境界データの大量複製 |
| `environment/` | 役割別ディレクトリの`Dockerfile`、配信設定、証明書生成、サービス初期化、OAuth代替。コンテナ内で動くコード | Playwrightの画面操作、ホスト側のCompose起動制御 |
| `scripts/` | Taskfileから呼ぶホスト側の処理。失敗伝播・成果物回収・後片付けなど、YAMLだけでは読みづらい制御 | テストデータの保存処理、ブラウザのassertion、Taskfileと二重管理する別の起動入口 |
| `artifacts/` | 固定の`report/`・`results/`へ最新の実行結果だけを保存 | テストの入力、再利用する認証状態、手編集するソース |

`tests/`と`contracts/`は`fixtures/`を利用できる。fixtureはspecをimportせず、spec同士もimportしない。複数specで必要になった準備・操作だけをfixtureへ切り出す。`environment/`へデータを渡す際はテスト専用の入力・結果の受渡しを明示し、ブラウザ側から環境スクリプトをimportしてDBに接続しない。

製品の`src/`からテストコードをimportしない。E2Eの期待値を製品の変換関数・認可関数で計算すると同じ不具合を見逃すため、E2Eは確定した仕様に基づく期待値と公開されたHTTP・UIを使う。

### ファイルとディレクトリの増やし方

1. 業務specは最初の一つから`tests/<機能名>/`・`contracts/<機能名>/`に置く。機能名は上の配置先を使い、未実装機能の空ディレクトリは作らない。Issue番号・画面URL・HTTPメソッド・成功／失敗による階層は作らない。環境疎通だけは`tests/environment.spec.ts`に置く。
2. `tests/knowledge/create.spec.ts`・`update.spec.ts`のように利用者の操作で分け、同じ操作の正常系・異常系は同じspecへまとめる。`contracts/`はAPIのリソース・操作で分け、例えば`knowledge/create.spec.ts`に該当するステータス・JSON・ヘッダーのケースをまとめる。テスト名は下記の命名規約に従い、条件と期待結果を一文で表す。
3. 複数画面を通るシナリオは、主な検証結果を所有する機能へ置く。例えば編集後の公開結果が主目的ならpublic-knowledgeへ置く。同じフローを画面ごとに複製せず、共通IDで関連付ける。新しい機能分類が必要な場合は、その所有する結果と既存分類で扱えない理由を本書へ追記する。
4. 小さなspec固有の準備はspec内に置く。共有するデータや認証補助は`fixtures/<データを所有する機能>/`へ置き、`types.ts`、`users.ts`、`scenario.ts`、`prepare.ts`など責務でファイルを分ける。公開閲覧で使う知識データも`fixtures/knowledge/`を再利用する。知識の入力生成から`auth/users.ts`を利用してよいが、認証fixtureは知識fixtureへ依存させない。トークン固有の準備・解放は`mcp-tokens/`へ追加する。
5. fixture共通のブラウザ基盤だけは`fixtures/test.ts`に置く。`helpers/`・`utils/`という目的の分からない置き場や、全機能を集約する巨大なtypesファイルを追加しない。機能内でさらに分ける場合は、独立した責務が生じた時点で検討する。
6. 固定ファイルは形式別の`files/markdown/`・`files/html/`へ置く。例えば`html/script-attempt.html`のように内容の目的を名前で示す。形式内で多数の用途をまとめる必要が生じた場合に限り用途別に分割する。サイズ境界の大きなデータはテスト専用の一時領域へ生成・削除し、共有サンプルを書き換えない。
7. `environment/`は上記のサービス・役割単位で配置する。各役割のDockerfileは原則`Dockerfile`とし、複数役割で共有するものだけ用途を接尾辞で示す。現在は`init/Dockerfile.tools`をinitとOAuthで、`proxy/Dockerfile`をproxyと証明書生成で共有する。ディレクトリ分割とイメージ分割は別の判断であり、必要な依存・ビルド責務が変わる場合にイメージを分ける。証明書そのものは実行専用volumeへ生成する。
8. `scripts/`は直下配置を基本にする。ホスト制御が独立した複数の責務へ増えた場合にだけ分割する。単なる一行コマンドのラッパーやTaskfileと別の起動入口は作らない。
9. `artifacts/`は直下の`report/`・`results/`へ保存し、回収時に前回分を削除して置き換える。実行ID別の保存先は作らない。人が機能別へ並べ替えたり、手編集したり、入力として再利用したりしない。

移動・追加時はPlaywrightのtestMatch、E2Eのtsconfig、DockerfileのCOPY、Composeのcommand・build context、Taskfile、importと文書リンクを確認する。現在の`init/Dockerfile.tools`は`init/*.mjs`・`oauth/*.mjs`をそれぞれCOPYするため、さらに階層を増やす場合はCOPYと起動パスも更新する。探索条件を広げて`.example`や成果物を誤実行しない。

### テスト名の書き方

`test("条件と期待結果を表す日本語の一文", ...)`を基本とする。名前だけを読んで、どの状態・入力で何が起きることを確認するのか分かるようにする。定型の区切り記号を増やさず、自然な文章でつなぐ。

- 例：`未ログインでも、HTTPSでログイン画面を表示できる`。
- 例：`他人の知識を更新しようとすると、拒否され保存内容が変わらない`。実装する際は対応するAPI契約をIssueで確定する。
- `ENV01`・`X02`・Issue番号などの管理IDや、正常系・異常系だけの分類をテスト名に付けない。対応はspecのコメントに日本語のシナリオ名と一緒に記載する。
- 一つのtestは一つの条件と期待する振る舞いを扱う。同じ結果を確かめる複数assertionはまとめてよいが、独立した画面表示・API疎通などを一つの名前へ詰め込まない。
- `describe`は関連ケースのまとまりを示す必要があるときだけ使い、使う場合もtest名から条件・期待結果を省略しない。階層をたどらないと意味が分からない名前にしない。
- パラメータ化したテストも、人が分かる入力の特徴と期待結果を名前に含める。連番・内部ID・秘密値をそのまま埋め込まない。
- ブラウザ名はPlaywrightのproject表示に任せ、テスト名へ重複記載しない。

### 雛形と実装済みコード

`.spec.ts.example`はコピーして具体化するためのファイルであり、実行対象ではない。`fixtures/knowledge/prepare.ts`・`fixtures/auth/authenticate.ts`と`environment/init/business-seed.mjs`は入出力を示す呼出し可能な雛形で、未実装時は明示的に失敗する。ファイルの有無だけで機能が完成したと判断しない。

各Issueで初期状態・入力・期待結果を決めてから雛形を実装する。業務データ投入の順序はmigration → bucket作成 → seedとし、返すID対応表に秘密値を含めない。業務シナリオを有効にする変更では、一括コマンドのinitとtestの間にseedを接続し、失敗時にテスト開始へ進まないことを検証する。

### コマンドと文書の管理

実行手順・コマンド一覧は [E2E README](../dev/frontend/e2e/README.md) に集約し、実際の定義は [ルートTaskfile](../Taskfile.yml) を正とする。各層の検証方法は各層のARCHITECTURE.mdを参照する。ディレクトリやサービスを増やす際に、同じ手順を別のREADMEへ複製しない。

作成・修正時は [e2e-implement](../.agents/skills/e2e-implement/SKILL.md)、レビュー時は [e2e-review](../.agents/skills/e2e-review/SKILL.md) を利用する。スキルは作業手順を提供し、本書の規約を重複定義しない。

## CIと完了条件

現在のCIは [Frontend checks](../.github/workflows/frontend-checks.yml) と [Backend quality](../.github/workflows/backend-quality.yml) であり、横断検証は実行していない。フロントエンドの`test`は現状テスト0件でも成功する設定であり、これをE2Eへ引き継がない。

横断基盤導入後はpull requestとmainへのpushで実行する。初期はpath filterを使わず全Xシナリオと契約テストを実行する。Chromium・Firefox・WebKitを対象にし、依存・ブラウザ・コンテナを固定する。最低限、次をすべて満たして完了とする。

- 各層の既存検査とフロントエンドbuildが成功し、Compose build、空DBへのmigration、seed、readinessが成功している。
- 対象機能の契約テストとXシナリオが全対象ブラウザで成功している。0件、対象のskip、起動失敗、タイムアウトを成功にしない。未実装シナリオは明記し、その機能の完了を宣言しない。
- 自動retryは初期値0とする。調査のための再実行で成功しても最初の失敗を隠さず、原因を解消する。共有HTTP・認証・公開DTO・配信設定の変更はX01〜X07すべてを回帰対象にする。
- 失敗したテスト名・ブラウザ・期待結果・実結果がレポートで追跡でき、終了コードがCIへ伝わっている。後片付けは常に実施する。
- Cookie、OAuth code、Authorization、MCP平文、署名URLをログ・添付へ残さない。動画はブラウザ操作のあるテストで成功・失敗を問わず保存する。秘密値が画面へ表示されるテストは`test.use({ video: "off" })`を適用し、trace・スクリーンショットも無効にする。storage stateを成果物にしない。他のテストも添付前に秘密値がないことを保証し、診断成果物の保持期間は7日とする。

文書のみの変更は相対リンク、現行コマンドの実在、受け入れ基準との対応を検査する。アプリの振る舞いを変えない変更のためにE2Eを新設する必要はない。
